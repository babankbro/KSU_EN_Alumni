# 1. บทนำ (Introduction)

## 1.1 วัตถุประสงค์ของเอกสาร
เอกสารนี้ระบุความต้องการของซอฟต์แวร์ระบบสารสนเทศศิษย์เก่า คณะวิศวกรรมศาสตร์ มหาวิทยาลัยกาฬสินธุ์
เพื่อใช้เป็นข้อตกลงร่วมระหว่างผู้ใช้ ผู้พัฒนา และผู้ดูแลระบบ และใช้เป็นฐานในการออกแบบ พัฒนา ทดสอบ และตรวจรับ

## 1.2 ขอบเขตของผลิตภัณฑ์ (Scope)

**ชื่อระบบ:** KSU-EN Alumni

**ระบบนี้ทำอะไร**
- จัดเก็บและบริหารฐานข้อมูลศิษย์เก่าระดับคณะ พร้อมความสามารถในการ**สืบค้นแบบหลายมิติ (faceted search)** ตามแบบ CMU Entaneer
- เป็นช่องทางเผยแพร่ข่าวสาร กิจกรรม และ**ข่าวของศิษย์เก่า (Alumni News Feed)** ซึ่งศิษย์เก่าเป็นผู้สร้างเนื้อหาเอง
- เป็นช่องทางประกาศรับสมัครงานและฝึกงานจากศิษย์เก่าสู่รุ่นน้อง
- รวบรวมข้อมูลภาวะการมีงานทำเพื่อสนับสนุนงานประกันคุณภาพและการปรับปรุงหลักสูตร

**ระบบนี้ไม่ทำอะไร (Out of scope v1)**
- ระบบบัญชีและการเงินของสมาคมศิษย์เก่าแบบเต็มรูปแบบ
- การออกเอกสารสำคัญทางการศึกษา (transcript, ใบรับรอง) — ลิงก์ไปสำนักส่งเสริมวิชาการและงานทะเบียนแทน
- แอปพลิเคชัน native (ใช้ responsive web / PWA แทน)

**ประโยชน์ที่คาดหวัง**
- คณะมีฐานข้อมูลศิษย์เก่าที่เป็นปัจจุบันและใช้รายงาน QA ได้
- ศิษย์เก่ากลับมาเชื่อมโยงกับคณะและกันเอง
- นักศึกษาปัจจุบันเข้าถึงโอกาสฝึกงาน/ทำงานผ่านเครือข่ายศิษย์เก่า

## 1.3 นิยาม คำย่อ และคำศัพท์

| คำ | ความหมาย |

# 2. ภาพรวมระบบ (Overall Description)

## 2.1 มุมมองผลิตภัณฑ์ (Product Perspective)

KSU-EN Alumni เป็นระบบ**ใหม่ระดับคณะ** ที่ทำงานร่วมกับระบบเดิมของมหาวิทยาลัย ไม่ทดแทน

```
        ┌────────────────────────┐
        │ ระบบทะเบียน / CONGRATE  │ ── นำเข้าข้อมูลตั้งต้น ──┐
        └────────────────────────┘                        │
                                                          ▼
   ┌──────────────────┐     ┌────────────────────────────────────┐
   │  LINE OA          │◄───►│      KSU-EN Alumni System          │
   │ (Login/แจ้งเตือน)  │     │  ┌──────────────────────────────┐  │
   └──────────────────┘     │  │ Directory · News · Events    │  │
                            │  │ Jobs · Survey · Admin        │  │
   ┌──────────────────┐     │  └──────────────────────────────┘  │
   │ alumni.ksu.ac.th  │◄───►│                                    │
   │ (เว็บสมาคม ม.)     │     └────────────────────────────────────┘
   └──────────────────┘                    │
                                           ▼
                                 ┌────────────────────┐
                                 │ รายงาน QA / หลักสูตร │
                                 └────────────────────┘
```

**เหตุผลเชิงตำแหน่ง:** ระบบระดับมหาวิทยาลัย ([[Benchmark - KSU]]) เป็นเว็บประชาสัมพันธ์ ไม่มี directory ที่ค้นหาได้ ระบบระดับคณะจึงเติมช่องว่างนี้โดยไม่ทับซ้อน

## 2.4 สภาพแวดล้อมการทำงาน (Operating Environment)
- เว็บเบราว์เซอร์รุ่นปัจจุบัน (Chrome, Safari, Edge, Firefox) บนเดสก์ท็อปและมือถือ
- **ออกแบบแบบ mobile-first** — ศิษย์เก่าเข้าถึงผ่านมือถือเป็นหลัก
- ทำงานบนโครงสร้างพื้นฐานที่หน่วยงานไอทีของมหาวิทยาลัยดูแลต่อได้ (ดู [[Architecture]])

## 2.5 ข้อจำกัดในการออกแบบ (Design Constraints)

# 4. อินเทอร์เฟซภายนอก (External Interface Requirements)

## 4.1 อินเทอร์เฟซผู้ใช้
- ออกแบบ **mobile-first** responsive
- ภาษาไทยเป็นภาษาหลัก โครงสร้างรองรับการเพิ่มภาษาอังกฤษภายหลัง
- ให้ความสำคัญกับความเรียบง่าย เนื่องจากผู้ใช้หลักใช้งานไม่บ่อย (ข้อ 2.3)
- ควรผ่านแนวทาง WCAG 2.1 ระดับ AA เป็นอย่างน้อย

## 4.2 อินเทอร์เฟซซอฟต์แวร์

## 5.2 ความมั่นคงปลอดภัย (Security)

| รหัส | ความต้องการ |
|---|---|
| NFR-SEC-01 | รหัสผ่านต้องจัดเก็บแบบ hash ด้วยอัลกอริทึมที่เหมาะสม |
| NFR-SEC-02 | ต้องป้องกันช่องโหว่พื้นฐานตาม OWASP Top 10 |
| NFR-SEC-03 | ต้องจำกัดอัตราการเรียกใช้งานในจุดที่เสี่ยงต่อการดูดข้อมูลและการเดารหัส |
| NFR-SEC-04 | ข้อมูลที่ระบุตัวบุคคลต้องเข้าถึงได้เฉพาะผู้มีสิทธิ์ และต้องบันทึก log |
| NFR-SEC-05 | ต้องมีการสำรองข้อมูลเป็นประจำและทดสอบการกู้คืนได้จริง |
| NFR-SEC-06 | ไฟล์ที่อัปโหลดต้องตรวจชนิดจาก**เนื้อไฟล์จริง** (magic bytes) ไม่ใช่จากนามสกุลหรือ MIME ที่ผู้ส่งแจ้ง และตั้งชื่อ object ด้วย UUID ไม่ใช้ชื่อไฟล์ของผู้ใช้ |
| NFR-SEC-07 | ไฟล์ส่วนบุคคล (รูปโปรไฟล์ เอกสาร) ต้องไม่เปิดให้บุคคลทั่วไปเข้าถึง — bucket เป็น private และตอบ 404 แทน 403 เพื่อไม่ยืนยันว่ามีไฟล์อยู่ |
| NFR-SEC-08 | Session ของเจ้าหน้าที่ต้องเก็บในฐานข้อมูลเป็น **hash** ของ token เท่านั้น cookie ต้องเป็น httpOnly และหมดอายุภายใน 8 ชั่วโมง |
| NFR-SEC-09 | ระบบต้อง**ไม่เชื่อ** header `X-Forwarded-For` เว้นแต่ประกาศว่ามี reverse proxy ที่เชื่อถือได้ — ภายใน Docker ทุก request มาจาก IP เดียวกัน การจำกัดตาม IP จะกลายเป็นการล็อกเจ้าหน้าที่ทั้งหมด (พบจากการทดสอบจริง) |
| NFR-SEC-10 | ข้อความที่เจ้าหน้าที่กรอก (เช่นเนื้อหาข่าว) ต้องแสดงเป็นข้อความเสมอ ไม่ถูกตีความเป็น HTML |
